# 直播延迟与缓冲

当前播放侧默认值用于缩短启动探测、减少可积压量，不保证固定端到端延迟。

| 位置 | 当前设置 | 作用与限制 |
|---|---|---|
| `Demuxer.cpp` | `fps_probe_size=0` | 参数齐全后不额外等待帧率统计；日志 `probe_ms` 记录探测耗时 |
| 同上 | 探测上限 2 MiB / 3 秒 | 保留首关键帧与探测包，特殊/缺轨输入仍可能等待较久 |
| `audio.buffer_ms` | 100 ms | 应用 PCM 环容量；至少 4096 个每声道样本，SDL/硬件缓存另计 |
| `pipeline.video_queue_capacity` | 3 帧 | 显示前解码帧容量；满时背压，未来帧保留 |
| `VideoDecoder.cpp` | `FF_THREAD_SLICE` | 避免帧级线程额外缓存；部分码流并行能力可能下降 |
| `input.max_buffer_ms` | 2000 ms | 异常积压恢复阈值，不是启动预缓冲目标 |

输入流仍正常进行 B 帧重排并以音频为主时钟。
严重积压清两轨并等待关键帧；默认主播 GOP 为 2 秒，过小的恢复阈值可能增加等待/黑屏次数。
完整队列策略见 [线程说明](threading.md)，调度规则见 [音画同步](av-sync.md)。

旧本机日志曾同时出现约 1.2 秒压缩包缓存、0.48 秒应用 PCM、8 帧解码视频和约 1.6 秒开流探测，
指向播放侧积压；这是历史定位线索，不是当前默认值的实测结果。
音视频并行，不能把两路缓存时长直接相加；同一路串联缓存可用于估算，但仍不等于端到端测量。

排查时观察 `probe_ms`、`buffer_ms`、`audio_queued`、`frame_queue`，
并检查其他 JSON/命令行是否仍覆盖为旧值 500 ms / 8 帧。
实际采集到显示估计与钟差边界见 [性能统计](performance-statistics.md)。
约 0.5 秒是历史优化目标，不能由容量推导或保证；采集、编码、SRS、网络、调度和音频设备均会影响结果。
运行及 CMake 构建命令统一见 [README](../README.md)。

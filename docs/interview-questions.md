## 一、项目介绍与总体架构（01—10）

参考：[项目说明](../README.md)、[架构](architecture.md)、[媒体方案](../../方案.md)、[平台扩展方案](../../多人直播系统扩展方案.md)。

### 01. 请用一两分钟介绍项目，并画出完整架构。

**回答要点：** 分别画出主播、SRS、观众和业务后端；说明媒体数据通过 RTMP/HTTP-FLV 流转，账号与房间通过 HTTP/JSON 管理。客户端是统一应用，按开播/观看模式使用媒体模块；后端是独立进程。

**可能追问：** 一帧画面从采集到显示依次经过哪些对象、线程和队列？

### 02. 为什么做这个项目？它解决什么问题？

**回答要点：** 从“能推流、能播放”逐步做到“线程职责明确、缓冲可控、音画同步、可停止、可恢复”，再扩展多人独立直播与大厅选择观看。重点说明自己的学习目标和真实取舍。

### 03. 哪些是你实现的，哪些由第三方库完成？

**回答要点：** FFmpeg 提供采集适配、编解码、格式转换、封装和协议 I/O；SDL3 提供音频输出及 CLI 视频显示；Qt 提供界面和业务网络；SRS 接入与分发媒体。项目实现模块组合、时间轴、线程队列、同步调度、生命周期、恢复和业务状态规则。个人贡献按实际情况陈述。

**可能追问：** 既然 FFmpeg 能完成推拉流，你写的代码价值在哪里？

### 04. 为什么把媒体链路和业务控制层分开？

**回答要点：** 业务后端处理账号、房间、授权和状态，媒体流直接经过 SRS；数据库不承担音视频传输。现有 Session 接收配置启动媒体，不依赖 Qt Network 或 MySQL，便于 CLI、GUI 与平台复用。

### 05. 一个客户端同时有主播和观众功能，为什么还要分 publisher/player 目录？

**回答要点：** 可执行入口统一不等于职责混合。`publisher/` 负责生产和输出媒体，`player/` 负责输入和播放，`common/` 放共享基础设施，`apps/` 编排应用与平台流程。

### 06. 为什么选择 FFmpeg、SDL3、Qt、Drogon 和 SRS？

**回答要点：** 结合实际职责回答：FFmpeg 的媒体能力，SDL3 的音频回调与 YUV 显示，Qt 的桌面 UI 与异步请求，Drogon 的 HTTP 和异步数据库能力，SRS 的直播接入与分发。也要说明依赖体积、部署和版本适配的成本。

### 07. 项目当前支持哪些输入、输出和运行方式？

**回答要点：** 桌面/摄像头/本地文件，麦克风/WASAPI 系统回采；H.264/AAC；RTMP/RTMPS 推流，RTMP/RTMPS 或 HTTP/HTTPS-FLV 播放；GUI 与 CLI。本地保存目前是独立的纯视频 MP4 和纯音频 M4A，不能说已经保存为一个完整音视频 MP4。

### 08. “多人直播”具体指什么？是多人连麦吗？

**回答要点：** 当前平台设计是多主播分别开播、不同会话使用独立流名、观众选择某个主播观看。它不等于音视频会议，也未实现多人混流、连麦、回声消除或 WebRTC 通话。当前运行容量未实测。

### 09. 为什么使用 CMake？怎样支持客户端和后端独立构建？

**回答要点：** 以目标管理包含路径、依赖和编译选项；顶层组织媒体静态库与统一客户端，后端有独立 `CMakeLists.txt`。`LSL_BUILD_CONTROL_SERVER=ON`、`LSL_BUILD_MEDIA=OFF` 可只构建后端；GUI、测试也有独立开关。未额外编写构建脚本。

### 10. 项目哪些部分完成了，哪些还只能作为后续规划？

**回答要点：** 区分源码、编译、单项历史运行和完整平台验收。硬件编解码、WebRTC、多人连麦、集群和容量优化不能从方案推定为已实现；N07 未完成。性能目标也不能当成实测结果。

## 二、采集、预处理与基础数据（11—20）

源码入口：[`MediaInput.cpp`](../src/publisher/capture/MediaInput.cpp)、[`SystemAudioInput.cpp`](../src/publisher/capture/SystemAudioInput.cpp)、[`VideoPreprocessor.cpp`](../src/publisher/preprocess/VideoPreprocessor.cpp)、[`AudioPreprocessor.cpp`](../src/publisher/preprocess/AudioPreprocessor.cpp)。

### 11. Windows 桌面采集、摄像头采集、系统声音采集分别怎么实现？

**回答要点：** 桌面经 FFmpeg `ddagrab` 调用 DXGI Desktop Duplication 采集首个显示输出。摄像头和麦克风按设备后端打开，Windows 系统声音走 WASAPI loopback。各输入统一交付媒体帧，打开方式、格式与停止机制各有区别。

### 12. Windows 桌面帧怎样送到预处理？

**回答要点：** `ddagrab` 返回 D3D11 帧。采集模块将它下载成 CPU 内存中的 BGRA，预处理按目标分辨率缩放并转换成 YUV420P，再送入视频编码器。

### 13. RGB、YUV420P、NV12 有什么区别？为什么不能直接复制所有帧？

**回答要点：** RGB 按颜色分量表达；YUV 将亮度和色度分开。YUV420P 是 Y/U/V 三平面，NV12 是 Y 平面加交错 UV 平面；要考虑像素格式、平面大小、`linesize`、对齐甚至负步长。转换由 libswscale 完成。

### 14. 720p、25 FPS 原始视频大约占多少带宽和内存？

**回答要点：** 对 1280×720、8 位 YUV420P，忽略行对齐时每帧约 `1280×720×1.5 = 1,382,400` 字节；25 FPS 约 34.56 MB/s，约 276.48 Mb/s。8 帧约 10.55 MiB。RGB24、BGRA 和不同分辨率应重新计算，容器与分配开销另计。

**可能追问：** 为什么 8 帧的队列容量不能直接证明进程内存有上限？

### 15. 缩放为什么会变形？留黑和裁剪怎么选择？

**回答要点：** 原始桌面比例与编码目标不同时，直接拉伸改变比例；等比缩放留黑保留全部内容，裁剪填满目标但会丢边缘。项目提供对应预处理选项，输出仍要满足编码器尺寸和像素格式要求。

### 16. 音频 planar 和 packed 是什么？重采样只是修改采样率字段吗？

**回答要点：** planar 将不同声道分平面存储，packed 将声道交错存储；还要区分整型与浮点样本。libswresample 完成采样格式、采样率和声道布局转换，内部有滤波状态和延迟，不能只改元数据。

### 17. 音频为什么使用 FIFO？PTS 为什么按累计样本数计算？

**回答要点：** 采集块大小不一定等于 AAC 编码器的 `frame_size`，FIFO 负责拼帧。时间基为 `1/sample_rate` 时，PTS 可表示该帧首样本在共同时间轴上的位置，并随实际输出样本数推进。以 48 kHz、1024 样本为例，一帧约 21.33 ms；帧长应读取编码器协商结果。

**可能追问：** 输入停顿、样本重叠、最后不足一帧分别怎么办？

### 18. 采集帧率和目标帧率不同怎么办？

**回答要点：** 视频预处理依据时间轴整形，必要时丢帧或重复画面，保证输出 PTS 合理。重复帧不是新采集画面，统计时要区分采集 FPS、编码 FPS；延迟遥测也应保留原画面采集时间。

### 19. 本地文件作为直播输入时，为什么不能尽快读完？

**回答要点：** 文件 I/O 可能远快于实时；按媒体时间戳映射到单调时钟节奏读取，避免瞬时塞满下游和提前推送。文件循环要维护连续时间轴，EOF 要排空解码尾帧；非实时转换则可以采用背压尽快处理。

### 20. 声音很小是编码器出错吗？如何定位？

**回答要点：** 先看原始 PCM 与预处理后电平，再看增益、声道转换、编码解码后的电平和播放音量；能正常解码不等于电平正常。软件增益要考虑削波。历史低电平定位记录见 [音频诊断](audio-diagnosis.md)，不应承诺所有设备都已验证。

## 三、编码、时间戳与封装（21—30）

源码入口：[`VideoEncoder.cpp`](../src/publisher/encoder/VideoEncoder.cpp)、[`AudioEncoder.cpp`](../src/publisher/encoder/AudioEncoder.cpp)、[`RtmpPublisher.cpp`](../src/publisher/rtmp/RtmpPublisher.cpp)、[`VideoFileWriter.cpp`](../src/publisher/muxer/VideoFileWriter.cpp)。

### 21. PTS、DTS、time_base 分别是什么？

**回答要点：** PTS 是呈现时间，DTS 是解码时间，时间基定义整数时间戳的一格有多长；实际秒数为 `timestamp × num / den`。有重排时解码顺序与显示顺序可能不同。不同轨道的裸整数不能直接比较，应使用 `av_rescale_q()` 等转换。

**可能追问：** 为什么两条轨道不能分别把首 PTS 都归零？答：会抹掉原有音视频相对偏移。

### 22. FFmpeg 的 send/receive 为什么不能简单地“一进一出”？

**回答要点：** 编解码器内部有缓存和重排，一次输入可能暂时没有输出，也可能取出多个输出。send 返回 EAGAIN 时，应先 receive 取走输出，再重送未被接受的同一输入；receive 返回 EAGAIN 表示需要更多输入。不能直接丢掉该帧/包或无进展忙循环。

### 23. flush 是什么？正常 EOF 与重连 Reset 应怎样处理？

**回答要点：** 正常 EOF 向编解码器发送空输入，取出延迟数据直至 EOF，再处理重采样/FIFO 尾部。重连 Reset 撤销旧代次，丢弃旧延迟状态并重建，不能继续播放旧连接尾帧。编码 flush 与封装写尾是不同步骤。

### 24. I/P/B 帧、IDR、GOP 与直播延迟有什么关系？

**回答要点：** 从帧内/帧间预测和参考关系解释，不能把所有 I 帧都简单当成 IDR。GOP/关键帧间隔影响压缩效率、新观众首屏及故障后的可解码边界；B 帧重排可能增加延迟。当前低延迟编码设置关闭 B 帧，x264 可用 `tune=zerolatency`，但它不保证整条链路零延迟。

### 25. 为什么选 H.264 和 AAC？码率、分辨率、帧率、preset 如何取舍？

**回答要点：** 结合当前 FLV/RTMP 链路与兼容性回答。固定带宽下，分辨率/帧率越高，单像素或单帧可用比特越少；更慢的 preset 通常用更多 CPU 换压缩效率。应通过实际画面、编码耗时和码率观察选参，不能仅凭参数宣称质量达标。

### 26. SPS/PPS、extradata、AAC AudioSpecificConfig 有什么作用？

**回答要点：** 解码需要编码参数；FFmpeg 从编码器导出 `AVCodecParameters`，封装器据此写对应头部。认识 H.264 Annex B 与长度前缀表示、AAC ADTS 与容器配置的差别。当前由 FFmpeg 完成适配，不要声称手写了完整位流封装。

### 27. 为什么写封装头之后还要重新读取输出流 time_base？

**回答要点：** 封装器可能在 `avformat_write_header()` 中确定或调整流时间基。写包前从编码器时间基转换到最终输出流时间基，同时转换 PTS、DTS、duration，并设置正确 `stream_index`；不能假设所有输出都沿用编码器单位。

### 28. 为什么使用 av_interleaved_write_frame？能让音视频线程直接一起写吗？

**回答要点：** 它负责适当的跨轨交织，输入仍需正确的时间戳和轨道参数。项目将单个输出上下文交给唯一所属线程，音视频处理线程通过事件队列交付，避免并发修改封装状态。交织缓存也可能增加延迟。

### 29. 同时录制和推流如何避免一个 AVPacket 被两个输出路径破坏？

**回答要点：** 各路径创建独立 `AVPacket` 结构引用底层媒体缓冲，再分别改时间戳/轨道索引并交付。不能让两个线程共享同一个可变包结构；`av_interleaved_write_frame()` 对包引用也有消费语义，不能写完再当作原包继续使用。

### 30. MP4 为什么需要写尾？异常退出后能保证文件完整吗？

**回答要点：** 正常收尾需要排出编码尾包并让封装器完成索引等元数据。RAII 释放内存不等于业务层已成功 flush 和写尾。正常停止尽力完成本地文件，异常、中途磁盘失败或强制杀进程不保证完整；当前也不是断电安全录制方案。

## 四、协议、拉流和网络恢复（31—40）

源码入口：[`RtmpPublisher.cpp`](../src/publisher/rtmp/RtmpPublisher.cpp)、[`Demuxer.cpp`](../src/player/demuxer/Demuxer.cpp)、[`PacketBuffer.cpp`](../src/player/demuxer/PacketBuffer.cpp)、[`NetworkStatus.hpp`](../src/common/utils/NetworkStatus.hpp)。

### 31. RTMP、FLV、H.264 三者是什么关系？HTTP-FLV 又是什么？

**回答要点：** H.264 是视频编码，FLV 是封装格式，RTMP 是当前推流传输协议；HTTP-FLV 通过 HTTP 持续传输 FLV 媒体流。不能把编码、封装和传输混为同一层。两者在本项目中都由 FFmpeg 协议/格式层处理。

### 32. TCP 可靠，为什么直播还会卡顿？应用为什么还需要重连？

**回答要点：** TCP 保证有序字节传输不等于低延迟；丢包重传、队头等待、带宽不足会让媒体积压。连接也会因网络、服务和对端退出中断，应用需要超时、取消、缓冲限制与重建会话。

**可能追问：** TCP 粘包怎么处理？答：自定义 TCP 协议需自行做应用消息定界，本项目 RTMP/FLV 的解析交给 FFmpeg，并未自写通用 TCP 聊天协议。

### 33. SRS 在项目中做了什么？是不是每多一个观众都要重新编码？

**回答要点：** 当前使用 SRS 接收直播流并分发，未配置本项目自有的逐观众转码链路；主播不因观众增加重复编码。新增观众主要增加服务器连接、缓存和出口带宽，不能据此忽略服务端负载。

### 34. 推流断线重连时，需要重建哪些东西？

**回答要点：** 重建 FLV 输出上下文、AVIO、流和封装头，丢弃不可用的故障积压，从新视频关键帧建立共同恢复时间轴，并对齐音频。现有编码器和本地录制可继续工作；网络恢复不代表整条流水线每次全部重启。

### 35. 为什么不能把发送失败的包原样再发一遍？

**回答要点：** 失败时无法确定对端已收到多少数据，旧包可能不再属于新会话可用的参考链和时间轴。当前不承诺传输恰好一次，不盲目重发不确定包；直播恢复允许丢弃故障期间内容，优先恢复当前可解码媒体。

### 36. 队列积压时为什么不能随意丢压缩视频包？

**回答要点：** 预测帧存在参考依赖，随意丢包可能破坏后续解码。实时视频优先在编码前丢旧原始帧，播放侧也可在解码后丢迟到帧；严重压缩包积压需要共同清理并等待关键帧，不能只保留一个随机“最新包”。

### 37. FFmpeg 阻塞在网络读写时，停止按钮如何生效？

**回答要点：** 设置 `AVIOInterruptCB`，回调读取原子停止标志和截止时间；不在回调内加复杂锁、打印日志或释放上下文。所属线程退出 I/O 后负责清理；退避、等包和等关键帧也必须能取消。协作中断不保证强制打断所有系统调用。

### 38. serial 是干什么的？只清空队列为什么不够？

**回答要点：** 清空只能清掉仍在队列内的数据，解码线程可能已取出旧包，协调线程也可能持有 pending 帧。serial 标识媒体代次；断线、严重积压或跳变时递增，下游在交付与消费处核对，撤销旧包、帧、PCM、显示和时钟。

**可能追问：** 这和后端的发布连接代次有什么共同思想？答：均用于拒绝旧异步结果，但作用域与资源不同。

### 39. 指数退避怎么设计？连接成功就清零重试预算可以吗？

**回答要点：** 当前默认基础 1 秒、上限 30 秒，逐次翻倍并封顶，等待可取消；初次连接之外默认最多连续重试 5 次，具体以配置为准。要有有效媒体进展才恢复故障预算，避免反复“连上但不传媒体”导致无限重试。

### 40. 单次读写超时与无媒体进展超时有什么区别？

**回答要点：** 前者限制一次操作及其连续等待，后者检测连接存在但媒体不再有效推进。收到坏包、忽略轨道或一直等不到关键帧，不能一概视为有效进展；低帧率、长 GOP 要考虑相应时限。主动停止、可恢复错误和认证失败要走不同分支。

## 五、音画同步、音频输出与显示（41—50）

源码入口：[`AVSynchronizer.cpp`](../src/player/sync/AVSynchronizer.cpp)、[`SDLAudioSink.cpp`](../src/player/audio/SDLAudioSink.cpp)、[`VideoFrameQueue.hpp`](../src/player/pipeline/VideoFrameQueue.hpp)、[`SDLVideoRenderer.cpp`](../src/player/renderer/SDLVideoRenderer.cpp)。

### 41. 为什么选音频作为主时钟？视频提前或落后怎么办？

**回答要点：** 音频连续输出对停顿敏感，视频较适合等待或丢弃已解码帧。比较视频 PTS 与有效音频估计位置：提前则保留 pending 等待，明显迟到且有后继则丢帧，到时显示。当前调度结果包括 Wait、Drop、Render 和 Resynchronize。

### 42. 已解码音频样本数能直接代表扬声器播放位置吗？

**回答要点：** 不能，解码后还有应用 PCM 环、SDL 和设备缓冲。当前时钟从回调提交的媒体终点扣除 SDL 未消费量与估计设备周期延迟，并在回调间平滑推进；它仍是估计值，不是硬件物理播放指针。应用环尚未提交，不能重复从提交终点扣掉。

### 43. 什么时候使用 steady_clock，什么时候使用系统时间？

**回答要点：** 节奏控制、间隔、退避、速率和本地超时使用单调时钟，避免系统校时跳变；跨机器的采集到显示标记使用 Unix 时间，并依赖机器时钟同步；数据库业务时间统一 UTC。不能把不同机器的 steady_clock 数值直接相减。

### 44. 没有音轨、音频欠载或时钟不推进时怎么办？

**回答要点：** 有限等待后降级到单调外部时钟，让视频继续调度，恢复有效音频后再跟随。无音轨、关闭声音输出和音频自然结束也要覆盖。欠载补静音不能伪造媒体样本进度，否则视频会追随错误时钟。

### 45. 暂停、静音、音量为零、关闭音频有什么不同？

**回答要点：** 联合暂停冻结媒体节奏；静音或音量为零仍消费媒体并推进时钟；禁用音频输出走不同的设备和主时钟路径。直播长暂停仍受有限缓存约束，恢复可能跳过旧内容，不等于无限时移播放。

### 46. 为什么要同时限制包数、字节数、媒体时长和解码帧数？

**回答要点：** 包大小不固定，单纯限包数不能约束内存；同样大小的队列也不能限定媒体积压时长；解码后的帧体积又远大于压缩包。播放器分别限制接收包、解码帧和 PCM 缓冲，容量上限并不等于实际已排队延迟。

### 47. 怎么判断时间戳跳变？视频 PTS 跨度大就要重置吗？

**回答要点：** 要区分网络包层异常、调度层失步、正常未来帧和缺失时间戳。不能只凭队列 PTS 跨度大就丢所有未来帧。当前同步器结合实际主时钟误差、持续时间及音频 revision 决定恢复；恢复时共同换代，而不是只修视频一个变量。

### 48. SDL 音频回调为什么不能做解码、等队列或写耗时日志？

**回答要点：** 回调有及时供数要求，阻塞会造成欠载或爆音。项目在音频线程解码、重采样后写预分配 SPSC 环，回调只读取已有样本并交给 SDL。异常不能穿过 C 回调边界，错误要记录后交协调层处理。

### 49. SDL 和 Qt 两条视频显示路径有什么不同？

**回答要点：** CLI 可上传 YUV420P/NV12 纹理显示，减少额外 RGB 转换；GUI 经后台转换生成最新 RGB 副本，由 Qt 主线程绘制。处理平面、行跨度和等比缩放，不能把 FFmpeg 临时帧内存直接借给稍后绘制的控件。

### 50. 项目的音画误差、解码 FPS 和端到端延迟分别测的是什么？

**回答要点：** 音画误差是视频 PTS 减音频估计位置；解码 FPS 统计解码输出，不等于屏幕显示帧率。采集到显示估计依靠自定义 UUID 的 H.264 UDU SEI，把应用采集打戳与绘制完成时间相减；不含完整设备采集和物理显示链路，跨机有钟差，且要求编码/转发链保留标记。

## 六、C++ 所有权、并发与退出（51—60）

源码入口：[`FFmpegResources.hpp`](../src/common/media/FFmpegResources.hpp)、[`BoundedBlockingQueue.hpp`](../src/common/queue/BoundedBlockingQueue.hpp)、[`PublisherPipeline.cpp`](../src/publisher/pipeline/PublisherPipeline.cpp)、[`PlayerPipeline.cpp`](../src/player/pipeline/PlayerPipeline.cpp)。

### 51. 为什么用 RAII 和 unique_ptr？FFmpeg 的引用计数是否足够？

**回答要点：** RAII 处理结构和上下文生命周期，底层缓冲引用计数解决媒体数据共享，两者职责不同。FramePtr/PacketPtr 独占结构并使用正确 deleter；跨线程移动所有权，需要多份结构时 `av_frame_ref()`/`av_packet_ref()`。写共享缓冲前考虑 make_writable；AVStream、codecpar 等借用对象不能随意独立释放。

### 52. 为什么一个 FFmpeg 上下文只让所属线程操作？

**回答要点：** 编解码与封装上下文有状态，不能认为所有 API 天然可并发调用。按阶段独占减少同步和竞态；跨线程只提交数据、控制标志或快照。资源的 open/read/close 应保持归属，不由 UI 随时强行 free。

### 53. close、abort、clear 有什么区别？

**回答要点：** `close()` 禁止写入但允许排空；`abort()` 关闭并丢弃缓存；`clear()` 清缓存但不关闭。close/abort 唤醒生产者和消费者，队列不重新打开。abort/clear 将待释放资源换出后在锁外析构，缩短临界区。

### 54. 条件变量为什么要带谓词等待？notify_one 和 notify_all 怎么选？

**回答要点：** 线程醒来时条件不一定成立，要在同一互斥锁保护下重新检查容量、数据和关闭状态，覆盖虚假唤醒与并发消费。常规入/出队可通知对侧一个等待者，关闭/中止要通知所有等待者，防止退出时永远睡眠。

### 55. 队列满时为什么视频丢旧、音频背压、录制包等待？

**回答要点：** 实时原始视频优先新鲜度；音频随意删除样本块会破坏连续性；录制更重视完整输出。不同数据所处阶段和业务目标决定策略，不能使用统一的“满了丢最新”规则。慢磁盘仍可能沿共享输出路径传播背压。

### 56. mutex、atomic、volatile 分别适合什么？

**回答要点：** mutex 保护多字段不变量和容器；atomic 用于停止标记、计数或清晰设计的并发协议；volatile 不能替代线程同步。SPSC 环先写数据再 release 发布写位置，消费者 acquire 读取后再访问数据；复用槽位还需消费位置的对称同步。

**可能追问：** 原子计数都正确，为什么整个统计快照仍可能不一致？

### 57. 多线程出现死锁，你会从哪里查？

**回答要点：** 画锁顺序和等待图，检查锁内 I/O、锁内 join、回调重入、队列满/空与停止路径。项目外层策略锁到队列锁方向固定，音频 stream/device 锁也要遵守方向；通知停止应先于等待线程结束。

### 58. 怎样保证点停止或关窗口时不会卡住或出现 use-after-free？

**回答要点：** 先发停止与网络中断，关闭/中止队列解除背压，再 join 所有使用资源的线程，最后销毁上下文、音频流、回调 userdata 与 UI。GUI 保持事件循环轮询清理状态，不能在关闭事件里无限同步等待 HTTP 或工作线程。

### 59. 工作线程抛异常怎么办？为什么不能让异常逃出线程函数？

**回答要点：** 在线程边界捕获，保存首个 `exception_ptr`，发起全链路取消并唤醒队列，join 后由协调层重新抛出或转换为 Session 失败状态。未捕获异常会终止进程；线程创建到一半失败，也要回收已启动线程。

### 60. 正常 EOF、主动停止和异常取消为什么是三条不同路径？

**回答要点：** EOF 要排空采集解码、预处理、编码和输出；主动停止优先中断实时网络，尽力保全本地录制；异常可 abort 队列丢缓存。两轨输出必须等各自尾包后的 End，再由最后完成的轨关闭共享输出，避免音频或视频尾部被截断。

## 七、Qt 界面与异步业务请求（61—70）

源码入口：[`ApiClient.cpp`](../src/apps/platform/ApiClient.cpp)、[`LobbyControl.cpp`](../src/apps/ui/LobbyControl.cpp)、[`PublisherControl.cpp`](../src/publisher/ui/PublisherControl.cpp)、[`PlayerSession.cpp`](../src/player/pipeline/PlayerSession.cpp)。

### 61. 为什么界面线程不能直接跑推流循环？怎样让 GUI 与 CLI 共用代码？

**回答要点：** 长时间处理会阻塞 Qt 事件循环。Session 管启停、线程和快照，Pipeline 组织媒体处理；GUI 读取快照和画面，CLI 使用同一核心。窗口变化不应复制一套编解码业务逻辑。

### 62. 为什么只保留最新 GUI 帧，不对每帧都排一个 Qt 事件？

**回答要点：** GUI 绘制慢于后台生产时，逐帧排事件会增加内存和显示滞后。Mailbox 覆盖旧副本，Qt 定时取最新同步后帧，并用 revision/sequence 识别新帧；RGB 副本有额外转换开销，应承认取舍。

### 63. 页面已经关闭，HTTP 响应才回来怎么办？

**回答要点：** 请求关联 owner、取消状态和代次，使用 QPointer 等检测对象生命周期。迟到结果还要核对房间、会话与操作代次，不能打开旧房间或启动已取消媒体；单纯 abort 本地请求不能撤销后端已提交事务。

### 64. 旧账号请求返回 401，为什么不能直接清掉当前登录态？

**回答要点：** 用户可能已切换账号或重新登录。比较请求记录的 authenticationRevision 与当前值，旧鉴权结果作废，不能让旧 401 清除新令牌，也不能把旧账号数据应用到新页面。

### 65. HTTP 200 就代表业务成功吗？遇到非 JSON 错误怎么办？

**回答要点：** 同时检查 HTTP 状态、JSON 结构、业务 code 和必要 data；SRS hook 另有原生协议。框架或代理可能返回空体/非 JSON 4xx/5xx，要显示固定错误；还需总超时、响应体大小限制和取消。

### 66. 为什么 GET 可以有限重试，POST 开播不能直接照搬？

**回答要点：** 查询允许安全重复；写操作可能已经提交但响应丢失。当前通用层对特定临时失败最多重试一次 GET，包含 250 ms 间隔且共享原总时限；POST/PATCH 交由业务状态和请求 UUID 处理，401、429 不盲目重试。

### 67. 为什么带 Bearer 的业务请求禁止自动跟随重定向？

**回答要点：** 避免将凭证送往意外地址，也使 API 入口和协议行为明确。配置应指向最终可用入口；该策略配合令牌仅存内存、错误固定文案与日志脱敏使用。

### 68. 大厅卡片为什么不直接使用缓存的播放地址？

**回答要点：** 列表到点击之间主播可能下播、重连或开始新场次。卡片展示信息与播放授权/有效场次是不同检查；每次点击重新请求 playback，核对房间和当前会话，不对静态封面预先拉流。

### 69. 大厅刷新失败、正在观看时业务后端失联，分别怎么办？

**回答要点：** 大厅旧卡片标为缓存/未知并暂停新进入；已有媒体播放不因一次业务查询失败就强停。确认原会话终止或换场次才停止旧播放器及其自动重连。业务链路失联不等于媒体链路立刻中断。

### 70. 用户关闭窗口但下播请求没成功，如何收敛？

**回答要点：** 本地停止独立推进，远端只保留有限尽力处理时间；内存中按用户保存请求 UUID、已知会话 ID 和下播意图，重新打开可核对。整个进程崩溃后记录会丢失，靠服务端准备/重连时限和对账兜底，不能宣称凭此实现持久化恢复。

## 八、直播状态机与 SRS 一致性（71—80）

源码入口：[`LiveService.cpp`](../src/control_server/services/LiveService.cpp)、[`LiveRepository.cpp`](../src/control_server/repositories/LiveRepository.cpp)、[`SrsClient.cpp`](../src/control_server/srs/SrsClient.cpp)；契约见 [平台 API](platform-api.md)、[恢复行为](platform-recovery.md)。

### 71. 房间和一次直播会话为什么要分开？

**回答要点：** 房间是用户固定拥有的业务资源，会话是一场直播的生命周期；每场使用独立 session ID、流名和推流凭证。房间持有 `current_session_id`，下播保留历史会话，不用一份永远复用的流名代表所有场次。

### 72. 同一账号在两个客户端同时点击开播，如何避免出现两场有效直播？

**回答要点：** 事务中 `SELECT ... FOR UPDATE` 锁房间行，检查既有请求及有效会话，再插入会话、关联房间并提交；数据库的请求唯一约束和有效会话唯一约束兜底。只靠 UI 禁用按钮或进程内 mutex，无法覆盖多客户端和重启。

### 73. 开播接口超时，但服务端已创建会话，客户端怎么办？

**回答要点：** 同一次操作保持同一个 `client_request_id`，按个人房间和会话核实，区分本次申请与其他客户端会话。重复请求不创建第二场；终态旧请求不重新开播。因为推流凭证仅在创建成功时发一次，重试/查询不能恢复原明文 URL。

**可能追问：** 这是完整的“幂等返回相同响应”吗？答：保证不重复创建并返回可核对冲突状态，并不缓存和重放完整含凭证响应。

### 74. 为什么不是“开播接口成功就把房间设为 LIVE”？

**回答要点：** 申请成功只代表进入 PREPARING，客户端可能尚未采集或根本推不出媒体；SRS `on_publish` 允许接入也不等于已持续收到媒体。匹配服务实例、流和发布连接并观察音频或视频计数正增量后，才确认 LIVE。

### 75. 直播会话有哪些状态？为什么还需要 RECONNECTING 和 STOPPING？

**回答要点：** `PREPARING → LIVE`，短断线可进入 `RECONNECTING` 后恢复；主动停止进入 `STOPPING`，撤销发布权限并等待媒体确认消失，最终 `ENDED`；准备超时或开播失败可为 `FAILED`。RECONNECTING 保留宽限且不供新观众进入；STOPPING 避免已请求下播却再次接入。

### 76. 旧连接的 on_unpublish 迟到，怎样防止把新连接下播？

**回答要点：** 更新不仅匹配会话，还匹配 SRS server/service/client 身份、发布 generation 和记录 revision。新连接准入推进代次，旧回调与旧查询的条件更新应失败或安全忽略。回调顺序不能作为全局顺序依赖。

### 77. 有回调为什么还需要周期对账？

**回答要点：** 回调可能遗漏、重复、迟到，主播或服务异常退出时更明显。周期查询 SRS 当前流、连接及媒体计数，与数据库非终态会话核对；条件更新防止查询期间状态变化。默认约每 3 秒，不保证事件发生后精确某秒完成修正。

### 78. SRS 管理 API 暂时不可用，为什么不能把所有房间改成 OFFLINE？

**回答要点：** 无法观察与已确认断流是两种事实。标记媒体服务 UNAVAILABLE 并保留最后确认时间和会话状态，暂停发放新推流/播放信息，客户端显示未知；恢复后重新观察媒体进展，不能直接信任旧 LIVE。

### 79. 后端重启、SRS 重启、主播崩溃，分别如何恢复？

**回答要点：** 后端从数据库恢复非终态会话并完成新一轮对账；SRS 重启用 service_id 识别新实例，旧观察失效；主播崩溃依靠连接消失、媒体进展与宽限收敛。持久化截止时间跨后端重启保留，不能靠清数据库“恢复”。

### 80. 下播为什么先撤销权限，再关闭 SRS 发布连接？能保证远端操作完全原子吗？

**回答要点：** 先将 allow_publish 撤销并清摘要，阻止旧凭证再入，再关闭已记录的确切发布连接，等回调或对账确认结束。停止旧会话还需按旧 session 条件清房间关联。数据库更新与 SRS 删除不是同一事务；远端核对身份与删除之间仍有重启竞态，不能声称完全消除。

## 九、MySQL、账号与安全设计（81—90）

源码入口：[`001_initial_schema.sql`](../deploy/database/001_initial_schema.sql)、[`002_publish_connection.sql`](../deploy/database/002_publish_connection.sql)、[`AccountService.cpp`](../src/control_server/services/AccountService.cpp)、[`AccountRepository.cpp`](../src/control_server/repositories/AccountRepository.cpp)、[`RateLimiter.hpp`](../src/control_server/common/RateLimiter.hpp)。

### 81. 数据库有哪些核心表？注册为什么需要事务？

**回答要点：** users、auth_sessions、rooms、live_sessions，另有 schema_migrations 记录迁移版本。注册同时创建账号和唯一个人房间，应一起提交或回滚；用户名唯一、房间 owner 唯一由数据库约束保证，避免“先查不存在再插入”的并发漏洞。

### 82. active_room_id 生成列的唯一索引解决了什么问题？

**回答要点：** 非终态会话映射到 room_id，终态映射为 NULL；唯一索引使同一房间最多一条有效会话，同时利用 MySQL 唯一索引允许多个 NULL 保留历史。它补充事务逻辑，但不替代状态转换、鉴权和锁。

### 83. 为什么 rooms.current_session_id 使用复合外键？

**回答要点：** `(rooms.id, current_session_id)` 引用 `(live_sessions.room_id, id)`，保证当前会话属于这个房间；只有 session ID 外键无法表达房间归属。创建表时先允许空指针，待两表建立后添加约束，终态清理在业务事务中明确执行。

### 84. FOR UPDATE 与 revision 条件更新各解决什么？冲突后怎么办？

**回答要点：** 行锁串行化开播等需要检查并写入的同房间事务；`WHERE revision=? AND publish_generation=?` 让迟到异步更新不能覆盖新状态。条件更新影响零行时应认为观察已过期，重新读取/等待下一轮，不能无条件覆盖。事务尽量短，不持锁跨远端网络调用。

### 85. 大厅查询怎么建索引？以后数据多了 OFFSET 有什么问题？

**回答要点：** 结合当前 `status, started_at DESC, room_id DESC` 索引及实际 JOIN/排序分析，不能仅凭建了索引就说没有排序成本。当前使用分页且不承诺跨请求快照；未来大偏移可考虑稳定排序键的游标分页，但并非当前已实现。

### 86. 密码为什么使用 Argon2id，登录令牌却只保存 SHA-256 摘要？

**回答要点：** 人类密码熵低，使用带盐且有计算/内存成本的密码哈希抵御离线猜测；安全随机的高熵令牌可以用摘要查找和验证。两者都不保存明文，不能把 SHA-256 当成人类密码的充分存储方案。具体密码库由 libsodium 提供。

### 87. 为什么使用不透明 Bearer 令牌，而不直接使用 JWT？

**回答要点：** 首版单服务需要明确过期、撤销和退出登录，不透明随机令牌配数据库会话更直接。代价是认证查询依赖数据库。当前没有刷新令牌体系；令牌只在客户端内存，进程退出后重新登录，不能说登录态可跨重启恢复。

### 88. 为什么密码哈希要放工作线程？队列为什么有限？

**回答要点：** Argon2id 有意消耗 CPU/内存，在 Drogon 事件循环执行会拖住其他请求。当前专用密码工作线程为 2 个、待处理队列上限 16，满时返回忙；数据库调用仍异步。工作池参数是实现配置，不是已验证的登录吞吐指标。

### 89. 登录态、推流凭证、SRS hook 密钥为什么不能混用？

**回答要点：** 三者授权对象不同：用户业务 API、某场直播发布、SRS 与后端之间的可信通知。推流凭证绑定场次、流名、权限和有效状态；hook 同时检查直接来源白名单与共享密钥，不信任随意提供的转发头。公开播放不附主播凭证。

### 90. 项目如何防止 SQL 注入、爆破、越权和日志泄密？

**回答要点：** SQL 参数绑定，接口严格校验类型/范围/UTF-8；认证后检查资源所有者；登录/注册等有限流，密码工作池有界；应用日志、配置打印及 FFmpeg 诊断脱敏。SRS 日志需要单独部署处理。固定窗口限流是单进程实现，仍有窗口边界和多副本限制，不能当完整风控系统。

## 十、故障排查、性能与开放题（91—100）

参考：[黑屏与采集修复记录](m14-m15-fixes.md)、[延迟](latency.md)、[性能口径](performance-statistics.md)、[部署](platform-deployment.md)。

### 91. 讲一个你真正解决过的困难：为什么“有解码帧但一直黑屏”？

**回答要点：** 按“现象 → 分层数据 → 假设 → 修改 → 历史验证 → 限制”讲。旧策略按解码年龄/PTS 跨度淘汰尚未到播放时刻的帧，首个同步候选又被不断替换，导致无法完成显示。修复为有界帧队列背压、按播放时钟丢迟到帧、保留首次对齐候选，并让停止/换代可打断等待。

**可引用的历史记录：** 2026-10-26 同一 HTTP-FLV 合成输入下，修复前解码 437 帧、显示 0 帧；修复后约 90 秒显示 2199 帧，约 25 FPS。证据来自当时记录，不能替代当前统一 GUI 或完整 SRS 平台验收，也不能据此承诺端到端延迟。

### 92. Windows 桌面采集临时失败，怎么处理？

**回答要点：** 遇到可恢复的读取错误，在原采集超时预算内重建 `ddagrab` 采集图，保留共同时间轴。恢复等待可取消，持续失败会超时退出。首次打开失败时报告原始错误。

### 93. 用户说“有画面但直播越来越慢”，你会怎么查？

**回答要点：** 先区分画面时间滞后与音画不同步，再观察采集/编码速率、RTMP 队列、收包媒体时长、解码帧、PCM 与设备缓存。比较生产和消费速率，定位持续增长的阶段，再决定降负载、丢旧内容或换代；不能只增加缓冲。

### 94. 如何优化首屏和端到端延迟？能承诺 500 ms 吗？

**回答要点：** 分解采集、预处理、编码缓存、GOP 等待、SRS、网络、探测、包队列、解码、同步、音频设备和绘制。当前减少探测和应用缓冲、采用 slice 解码线程等只是优化措施；更小队列也可能增加欠载与恢复次数。没有实测不能承诺 500 ms。

### 95. 怎样证明“确实优化了”，而不是改了参数感觉更快？

**回答要点：** 说明后续验证设计：相同输入、配置和机器，明确测量起止点，收集启动耗时、延迟分布、队列、丢帧和资源占用；区分同机与跨机钟差，比较改动前后。自带 SEI 估计和外部拍摄/时钟画面可互补。这是面试回答思路，不表示本次已执行测量。

### 96. 一台服务器能支持多少主播和观众？1000 人各看 2 Mbps 要多少带宽？

**回答要点：** 仅视频 payload 理想估算约 `1000×2 Mbps = 2 Gbps` 出口，另加音频、封装/协议、重传及余量；入站取决于主播数。实际瓶颈还可能是连接、内存、CPU、内核与部署网络。当前没有压测，不能给出项目已支持的并发人数。

### 97. 如果要支持多台业务后端或多台 SRS，现在的设计哪里需要改变？

**回答要点：** 当前限定单业务进程、单 MySQL、单 SRS；多副本要处理对账任务协调、共享限流、状态条件更新、流路由与实例身份。更多观众可考虑边缘分发/CDN；需要先确定瓶颈和一致性要求。Redis、消息队列、负载均衡等都属于待设计扩展。

### 98. 如果要加硬件编解码、WebRTC 或连麦，你会改哪里？

**回答要点：** 硬编硬解涉及设备上下文、像素格式和 CPU/GPU 拷贝；WebRTC 涉及另一套媒体传输、反馈和连接建立；连麦还需混音/混流、时钟、回声消除等。可利用已有接口与模块边界扩展，但不能把“换个 URL”当作完整实现，这些目前不是已交付功能。

### 99. 为什么“本机能连”不等于别的电脑能用？/health 正常代表全部正常吗？

**回答要点：** `127.0.0.1` 指向各自机器；Windows、WSL、SRS、后端和其他设备的网络视角可能不同。业务地址与下发媒体地址都要客户端可达，还涉及监听、防火墙、端口和容器映射。`/health` 只证明进程响应，不证明迁移、认证、SRS 对账或媒体就绪。

### 100. 如果现在让你交付演示，你会先完成什么？项目最大不足是什么？

**回答要点：** 先如实说明完整平台尚缺运行验收；在获得测试授权后核对迁移、依赖与地址，验证“登录 → 两主播独立开播 → 大厅选择 → 多观众观看 → 下播撤下”，再验证响应丢失、断网、服务重启和退出，记录性能与边界。优先补证据和已知缺口，不用继续堆功能代替验收。

## 可以准备的三段深入讲解

### 讲解 A：媒体多线程与所有权

按下面的图，说明每个箭头传什么、队列满了怎么办、谁释放资源：

```text
视频采集 → 原始视频队列 → 预处理/H.264 ─┐
音频采集 → 原始音频队列 → 重采样/AAC ──┤
                                      ↓
                                输出事件队列
                                      ↓
                            唯一本地封装/输出线程
                              ├→ MP4 / M4A
                              └→ RTMP 包队列 → FLV/网络线程 → SRS

文件输入：单输入线程解复用/解码后按轨分流。
```

重点准备：移动所有权与缓冲引用、每个上下文的所属线程、音视频不同的背压策略、首错传播、EOF 排空与取消回收。

### 讲解 B：播放器为什么能同步并在重连后恢复

```text
网络线程 → PacketBuffer ─→ 视频解码 → VideoFrameQueue → 同步调度 → Qt / SDL
                       └→ 音频解码/重采样 → PCM 环 → SDL 回调/设备
                                                        ↓
                                              音频播放位置估计
                                                        ↓
                                           视频 Wait / Drop / Render

换代：serial 递增 → 撤销旧媒体与时钟 → 新参数/关键帧 → 恢复。
```

重点准备：媒体 PTS 与墙钟的区别、音频提交不等于实际播放、初始同步候选、音频失效降级、Reset 与正常 EOF 的区别。

### 讲解 C：一次开播跨多个系统如何收敛

```text
Qt：保存本次请求 UUID
 → 后端：事务锁房间，创建 PREPARING 会话，首次返回推流 URL
 → Qt：启动 PublisherSession
 → SRS：on_publish 请求后端鉴权
 → 后端：核对连接身份，周期查询媒体计数进展
 → 确认 LIVE → 大厅可见 → 观众重新请求播放信息

停止：本地停止并提交下播意图
 → 后端撤销发布权限 → 关闭匹配连接
 → 回调/对账确认媒体消失 → ENDED，按场次条件清理房间关联。
```

重点准备：每个箭头失败会怎样、哪些数据持久化、哪些只在内存、重复操作如何处理、旧异步结果怎样失效。不要把数据库与 SRS 描述为同一个原子事务。

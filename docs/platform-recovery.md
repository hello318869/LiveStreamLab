# N06：恢复行为与部署边界

本文件描述客户端、业务服务和 SRS 适配的恢复规则，以及部署者需要保留的配置。
这些规则属于代码与静态检查结论；CMake 编译不替代实际断网、重启、多客户端或退出验收。
本轮未运行测试、程序或业务接口，未执行 SQL，也未应用部署模板或操作现有服务。

## 请求超时、重试和迟到结果

Qt 网络请求异步执行，页面销毁或取消会抑制旧回调；大厅/播放流程同时检查请求代次、房间和会话标识。
登录状态变化后，旧鉴权响应只返回 `AUTHENTICATION_CHANGED` 和空数据，
使界面能结束等待而不采用上一个账号的数据，也不会因为旧请求的 401 清掉新的登录令牌。
登录令牌只保留在当前客户端内存，退出登录清除本地状态；关闭整个程序后重新登录。

可安全重复的 GET 在网络失败或 HTTP 502/503/504 后最多重试一次，间隔 250 ms，
两次尝试共同使用原 `request_timeout_ms` 总时限，不是每次重新获得一份时限。
401、429、协议错误不会自动重试；POST/PATCH 不由通用网络层重复提交。
取消本地请求不能撤回服务器已经提交的事务，因此开播失败或超时后还要按请求 UUID 查询处理。

业务入口禁止自动跟随重定向，避免将 Bearer 令牌发给其他站点；
超时、非 JSON HTTP 错误、非法业务响应和超大响应均以固定错误信息呈现。
平台入口应直接指向最终可用地址；改动 `platform.local.json` 后重启客户端。

## 主播开播与下播

每次新开播操作先在当前用户的内存恢复记录中保存 UUID，再申请会话。
确认成功后记录本次会话 ID，使用返回的推流 URL 启动原媒体流水线；
恢复记录不保存密码、Bearer 令牌、推流 URL 或推流凭证。

| 情况 | 客户端处理 | 后端兜底 |
|---|---|---|
| 申请响应丢失 | 保留同一个 UUID；查询个人房间与会话，区分本次申请和其他客户端会话 | 房间行锁、请求唯一约束和既有会话冲突阻止并行开播 |
| 申请未成功 | 不启动媒体；明确错误可修正后新开播，未知结果先核对 | 无发布进展的准备会话按准备时限结束 |
| 本地媒体启动失败 | 停止本地会话，并尝试取消能够确认归属本次的准备会话 | 未成功回收的 `PREPARING` 最终按时限失败 |
| 点击停止时业务断网 | 本地采集/编码/推流仍可停止，记录下播意图，后续查询确认再重试 | 发布丢失后进入重连流程，宽限到期结束；不能把业务断网直接等同于全部下播 |
| 下播响应丢失 | 先查询确切会话；确认仍有效、允许发布时才再次提交停止 | 首次接受停止后撤销发布权限；重复停止返回当前状态 |
| `409` 指向其他请求 | 提示已有会话，等待用户明确选择结束，不自动下播 | 原有效会话继续存在 |
| 会话已 `STOPPING/ENDED/FAILED` | 停止旧媒体重连；再次开播需新会话/流名/凭证 | 终态或停止状态拒绝再次发布 |

一个自动恢复或手动重试周期最多提交三次停止请求，每次再次 POST 前先成功 GET 核对匹配会话。
未完成的房间初始化或下播意图按 `room_refresh_ms` 间隔继续查询；
网络层本身不会对停止请求进行无条件重放。

已知会话通过自己的会话 ID 查询；没有收到会话 ID 时，通过个人房间定位当前会话，
再比较 `client_request_id`。仅能确认属于本次操作的会话才能自动回收。
其他客户端创建的准备会话或已开播会话不能因为本机重试、返回或退出登录而被自动结束。

恢复标识和下播意图按用户保留在当前 `ApiClient` 内存中，跨工作窗口关闭和重新打开仍有效；
退出后同账号重新登录可以继续核对，另一账号不能使用前一账号的记录。
关闭窗口最多为远端保留 `min(request_timeout_ms, 2000)` 毫秒的尽力处理机会，
本地媒体回收完成后即可销毁窗口，不等待远端 `ENDED`；未完成的请求取消，恢复记录保留。
取消的申请没有获得场次 ID 且房间确认为离线时，普通开播暂不生成新 UUID。
用户可点击“核实并结束上次申请”，明确使用原 UUID 提交以核实最终结果；
若此前申请根本没到达服务器，可能新建一场准备会话后立即停止，期间不会启动采集或推流。
已有会话或终态按同一 UUID 返回，不会因核实创建两场直播，其他请求的会话也不会被自动结束。
整个客户端进程退出、崩溃、被强制杀死或机器断电后，这些内存记录不再存在；
不会把令牌或凭证写入磁盘来假装实现崩溃后无感恢复。
重新登录可查看自己的有效会话，并由用户明确选择结束或等待服务端时限收敛。

## 大厅与观看

大厅可见时按配置刷新，隐藏时停止刷新，同类请求未结束时不叠加。
刷新失败后，旧卡片显示为缓存/状态暂不可确认并停止供新进入使用；
不能保留旧的绿色“正在直播”外观让人误以为刚刚确认在线。
再次刷新成功后才采用新的列表状态。

点击卡片重新获取播放信息。房间已经结束返回 `ROOM_NOT_LIVE`，SRS 状态不可确认返回 503；
二者都不使用旧列表地址强行拉流。进入播放器后不继续刷新整份大厅列表，
仅查询当前房间，返回时等待旧 `PlayerSession` 完成回收后展示大厅。

正在观看时，业务查询失败或 `RECONNECTING` 只更新提示，不凭此将直播判定为结束。
确认当前会话 `STOPPING/ENDED/FAILED`，或房间已经切换到另一个会话，
才停止旧播放器并撤销其旧地址自动重连。
播放器的构造、启动、停止完成后的销毁继续在 Qt 主线程执行。

## 业务服务、数据库和 SRS 恢复

`/health` 只说明 HTTP 进程能接收请求，不能说明数据库已迁移、SRS 已鉴权或媒体已经上线。
业务服务启动时读取数据库非终态会话并开始对账；
恢复后，数据库里原有的 `LIVE` 也必须重新观察到匹配发布连接的音频或视频计数增量，
才能恢复对外的 `AVAILABLE`。不能因为持久化状态写着 `LIVE` 就立即发放播放地址。

| 故障或事件 | 收敛规则 |
|---|---|
| SRS API 或数据库查询失败 | 标记媒体服务 `UNAVAILABLE`，保留最后确认状态，不批量写入终态；暂停发放新推流/播放信息 |
| 查询恢复 | 清空跨故障的连续观测基线，重新核对服务实例、流和发布连接，重新观察媒体增量 |
| 业务后端重启但 SRS 仍收流 | 从数据库恢复当前会话和连接信息；完成新一轮媒体进展确认后开放准确业务状态 |
| SRS 重启 | 新 `service_id` 废弃旧实例观察；只有有效会话的合法重新发布可以再次准入 |
| 合法发布短断线 | 进入 `RECONNECTING`，宽限内允许同会话重连；匹配连接出现媒体进展后恢复 `LIVE` |
| 旧连接停播回调/旧异步查询迟到 | 按会话、服务器实例、发布连接、发布代次和记录版本条件更新，不能覆盖新连接 |
| 主播异常退出 | 遗漏回调由对账纠正；已收流会话按断流和重连规则结束，未开始会话按准备超时失败 |
| 已请求下播但 SRS 不可达 | 先撤销发布权限、进入 `STOPPING`，等待恢复后按记录连接关闭并确认消失再结束 |

默认首次推流等待 120 秒、重连宽限 20 秒、无媒体进展 15 秒、对账约每 3 秒。
这些是配置时限，实际状态变化还受查询成功、调度、网络和数据库时延影响，
不能承诺从故障发生的同一时刻精确计时或在某一秒完成撤下。
已经写入数据库的截止时间会跨服务重启保留；服务失联期间无法确认的媒体状态，
必须等管理连接恢复后继续核对，不能用清空房间或重建数据库恢复大厅。

SRS 的媒体计数只证明适配版本收到了受支持的音频/视频消息，不等于客户端已显示首帧。
SRS 删除指定发布客户端的 API 不支持原子地附带服务器实例条件；
当前实现先核对身份，再删除，并等回调/对账确认，仍存在远端恰好在两步之间重启的竞态。
首版限定单业务进程、单 MySQL、单 SRS，不提供多副本协调或自动故障转移。

## 客户端退出与服务进程管理

普通应用退出经过当前工作窗口的异步停止和资源回收，再结束 Qt 事件循环。
Windows 会话结束通知仅执行尽力停止，不能阻止系统关机，也不能保证所有 HTTP 请求和线程清理都有机会完成。
使用的通知接口为 [Qt 会话管理](https://doc.qt.io/qt-6/qsessionmanager.html)，本项目不阻止系统关机或执行同步网络等待。
任务管理器强制结束、崩溃和断电同样依赖后端恢复规则，不声明客户端总能发出下播请求。

[systemd 模板](../deploy/systemd/) 只提供进程启动、普通用户权限、失败重启和有界停止等待。
停止服务或达到重启频率上限后，不会自动删除数据库状态。
启动顺序为数据库、SRS、业务后端；后端启动排序与媒体业务可用性是两个条件，
只有完成对账和新媒体观察后，客户端才能按正常状态申请开播/观看。

升级保存 `/etc/livestreamlab/server.json`、`control-server.env`、
`srs-platform.local.conf` 和数据库；客户端保存各台机器自己的 `platform.local.json`。
更新默认模板不覆盖这些本机文件。回调密钥轮换需要同步修改后端环境和 SRS 两个 URL，
安排单独维护窗口，不在普通二进制升级时随机重建密钥。
业务后端单独升级不必重启正常收流的 SRS。
